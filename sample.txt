Investigation 2: GPU vs CPU Work
From the previous investigation, we can segment GPU vs CPU operations by the PID. While this investigation is not crucial for understanding the validity of hypothesis 1, it will be useful for future work
Some aspects of the trace do not reflect ‘real work’ (emboldened) done by the GPU or CPU, a brief (rough) description of each category is provided below:
`cpu_op` – CPU tensor operations  e.g. tensor reshaping, type casting, small math ops, and some dispatcher functions
`cuda_runtime` – CUDA runtime API calls from CPU to launch/manage GPU
`cuda_driver` – low-level (below runtime^) CUDA driver API calls
`kernel` – GPU kernel executions e.g. matmul, elementwise, reduce kernels
`gpu_memcpy` – Memory transfers on/between GPUs, device-to-device copies?
`gpu_memset` – GPU memory initialisation e.g. zeroing buffers
`cuda_sync` – GPU synchronisation events, overhead for parallel compute
`python_function` – parent events, contain all encapsulated work
`cpu_instant_event` – tracking memory usage (allocation/deallocation)
`ac2g` – links GPU-side kernel execution to CPU-side CUDA API call
`user_annotation` & `gpu_user_attention` – user-inserted profiler markers






Further investigation on specific operations within these categories, their average duration, scalability, etc, will be reserved for later work/benchmarking.

Investigation 3: Alternative Parallelism
Two types of ‘alternative parallelism’:
Different frameworks – HuggingFace’s functions may implement model parallelism in a way that specifically results in one device trace
Different strategies – It may be that model/pipeline parallelism itself is the issue since, for a single pass, only one GPU is active at a time
Best strategy to isolate how each affects trace generation would be to test multiple frameworks across a range of parallelism techniques
Candidate frameworks: PyTorch Native, DeepSpeed, MegatronLM
Seems that MegatronLM has some disadvantages for a quick test:
Some model code rewriting necessary
Checkpoint conversion issues???
Limited official support (GPT, BERT, T5, some LLaMA) 
Parallelism decided before loading the model?
More complex launching and debugging?
MegatronLM seems to be more specifically designed for training from scratch, perhaps not well-suited to this test
Not all parallelism strategies have communications in the forward pass (which is all we care about in the inference case)  and we would like to observe communications to ensure they are correctly preserved in the Chakra traces (and therefore also astra-sim) so we restrict ourselves to those that do for this testing, some of which are enumerated below:
PyTorch: FSDP (sharded-data), TP (tensor), PiPPy (pipeline)
DeepSpeed: ZeRO-3 (other strategies only have comms for backward pass?)
Run into many issues with the tested strategies, for example:
Requiring memory buffer for optimiser states even if using for inference
Loading entire model onto CPU and temporarily requiring enough storage on the GPU to load the whole model? Not clear why/if this is a bug
Manually moving embedding layers and outputs? Not clear if bug
Errors due to mismatch in expected labels for layers, not label agnostic?
^Some of the eros may be because the tooling for a couple of the techniques is still nascent and being developed

FYI: threads –> warps –> blocks –> grids
def:   [SW]     [HW]      [SW]     [SW]
Threads – smallest unit of execution, have their own private registers, and are executed as part of a warp
Warps – collections of 32 threads within a block, where all threads in a warp execute the same program concurrently (Single-Instruction Multiple-Threads)
Blocks – groups of threads executing together on the same SM (streaming multiprocessor), able to sync with each other, and sharing fast memory. Multiple blocks can reside on a single SM simultaneously
Grids – collections of independent blocks, across different SMs, unable to synchronise between blocks within a single kernel launch
SMs – fundamental processing units that execute blocks, each containing many SIMD execution lanes (CUDA/equivalent cores), a large register file, some shared memory (SRAM, often unified with L1 cache), warp schedulers, load/store units, etc
Cores – SIMD execution lanes inside an SM that perform arithmetic and logic operations. They don’t own threads, instructions issued for a warp are executed in parallel across many cores, with threads being dynamically mapped onto available cores. Cores don’t hold state, and cannot synchronise
GPUs: threads –> warps –> blocks –> grids
TPUs: operations –> tiles –> systolic arrays?
CPUs: instructions –> threads –> cores –> sockets?
Launch geometry factors and the resulting occupancy factor into kernel optimisation but are not the sole – or even biggest – constraint (depends on bottleneck e.g. latency, memory, compute, occupancy). Optimising memory behaviour and algorithm/instruction efficiency are crucial.

REF: https://arxiv.org/pdf/1612.09375 (one of the best introduction, by Tom Leinster (here he spawns again))
How may it help? (bullet point for people who know nothing about category theory, written for pedagogical purpose and to shape the research narrative. It is to build intuition.)
Motivated definition: The aim of category theory is to construct an abstract space where systems of study are categories and relations (functors) between those categories. A category is a set of elements called objects alongside a collection of morphisms between each pair of objects.  
One of its powers lies in its universality, illustrated  by universal property. Results in one category can be conveyed in other categories (not all). For us category theory will help us to generalize results obtained on a given class of workloads (i.e. workloads operating on sets) to other classes.
If a universal workload representation (and not universal representation) would be a formal, abstract model that captures the structure and interactions of any workloads, independent of its implementation that help us reason about, compare, compose or transform workloads then category theory naturally aligns with this aim.

------------------------------------------------------------------------------------
Universal properties
				   
------------------------------------------------------------------------------------

Categories: A category is a collection of objects, maps, or arrows, or morphisms and identity laws, endowed with a composition function ◦ such that:
For any triplets of objects A, B, C and any maps f: A -> B, g: B -> C, the function g◦f: A -> C is a map.
The composition of maps is associative.
For any map f: A -> B, there are identity laws: f ◦ 1 = f = 1 ◦ f


“A category is a collection of objects related to one another to a greater or lesser degree; a discrete category (i.e. a category containing no maps at all apart from identities) is the extreme case in which each object is totally isolated from its companions.”
Isomorphisms, dual category, principle of duality

------------------------------------------------------------------------------------

Functors: For any pair of categories, a functor F from one category to the other is a function sending any object of the former to an object of the latter category such that:
 For any pair of objects A, A’ of the first category, each arrow from A to A’ has an image by F which is an arrow from F(A) to F(A’). The image of this arrow f is noted F(f).
For any pair of arrow f,f’ in the first category F(f◦f’)=F(f)◦F(f’).
For any object A of the first category, the identity map of A is sent by the functor onto the identity map of F(A).
CAT (category of categories)
forgetful functors, free functors, presheaf
Faithful functors, full functor 

“We can tell a lot about a space by examining the functions on it. The   importance of this principle in twentieth- and twenty-first-century mathematics can hardly be exaggerated.”
